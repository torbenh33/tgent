# Agent continuation: budgets and repository synchronization

This note records the implemented continuation behavior and the worker instruction for repository-sync continuations. It is about continuation mechanics, not the separate policy for which lifecycle states may be recovered.

## Model-call and runtime budgets

There are two distinct paths (`agent_controller.py`, `AgentController.continue_agent`):

- **Live waiting worker:** continuation appends messages to the existing history and queues them to the existing worker (`review_feedback`). It does not call `start_agent` or alter the limits/counters. Model calls remain charged against the same `max_model_calls`, and the original runtime timer continues; no call or time budget is added or restarted. The controller checks the per-runtime call count in `_model_complete`; it increments before invoking the provider, so a failed provider invocation also consumes a call.
- **Inactive recovery:** continuation creates a new agent ID via `start_agent`, from the saved history plus continuation messages and saved project snapshot; the new record starts with `model_calls: 0` and a new runtime timer. It does not pass the original agent's `limits` or spent-call count. The normal start defaults therefore apply: at most `min(200, controller.max_model_calls)` model calls and `min(43,200 seconds, controller.max_runtime_seconds)` runtime (12 hours before controller caps). An explicit start request can ask for larger limits, but these continuation paths do not pass one. The new child inherits the original model/reasoning effort unless overridden through the controller API; this does not preserve the parent's budget. `restart_agents` is a convenience recovery path for stopped agents: it calls `continue_agent` with a “Resume the previous task” message and therefore gets the same fresh child budget. The child records `parent_agent_id`; the original history/snapshot is retained.

The public MCP `continue_agent` and `restart_agents` operations do not expose budget parameters. The controller's internal continuation method accepts model/reasoning overrides, not budget overrides. Controller defaults/caps are configured in `AgentController.__init__`; start-request validation and metadata initialization are in `agent_controller.py` (`_validate_start_request` and `start_agent`).

## Repository HEAD and sync behavior

A continuation is **not generally refreshed from the current source checkout HEAD**:

- Local continuation starts an inactive child from the parent's saved snapshot (`snapshot_project`), not a fresh copy of the controller's project checkout. Live continuation does not replace the worker's project tree.
- Remote continuation without an upload likewise uses the saved snapshot. With a `project_root`, `RemoteAgentAdapter.continue_agent` reads the agent's recorded `base_commit` and project name, then `_sync_project` pushes that recorded commit to `refs/agent-sync/<base>` and uploads current working-tree files (rsync excludes `.git`). On the service, those files are overlaid onto a new snapshot of the saved project; Git metadata is not replaced by the uploaded checkout. This is a file sync against the recorded base, not an automatic move of the agent's Git HEAD/ref to the caller repository's current HEAD. A live review-waiting agent deliberately skips this replacement; the controller rejects `sync_checkout` for a live worker.

The worker's `SYSTEM_PROMPT` in `agent_worker.py` separately instructs it, **for continuation syncs**, to fetch `/run/agent-sync/repository.bundle` and rebase onto “the supplied sync base commit”; it says the bundle is read-only. This is an instruction the worker is given, not evidence that the worker itself creates the bundle or discovers an arbitrary repository's HEAD. No implementation of `repository.bundle` or of the sync-base injection was found in the repository search for the continuation paths; that part is evidently supplied by the continuation runtime/environment or remains outside this repository's implementation. The prompt does not tell the worker to rebase onto the latest source HEAD; it names the supplied sync base commit.

Relevant implementation: `agent_controller.py` (`continue_agent`, `restart_agents`, `start_agent`, `_model_complete`, `_enforce_runtime_limit`); `remote_agent_adapter.py` (`continue_agent`, `_sync_project`); `remote_agent_service.py` (`_continue`); `agent_worker.py` (`SYSTEM_PROMPT`). The controller tests `test_agent_controller.py::test_continue_inactive_agent_starts_child_from_snapshot` exercise inherited history/snapshot and child creation; `test_remote_agent_adapter.py::test_continuation_pushes_recorded_base_and_transfers_again` and `test_live_review_continuation_does_not_replace_agent_worktree` cover remote sync selection and live review behavior. These tests do not assert model-budget values or the runtime-provided bundle mechanism.
