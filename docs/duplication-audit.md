# Code-duplication audit (2026-05-07)

Read-only audit of the current tree. No implementation behavior was changed. This is a targeted maintainability review, not a claim that similar code is interchangeable: the separate local and remote paths have different trust and transport responsibilities.

## Ranked summary

1. **Atomic persistence primitives (high value, medium effort):** `agent_store.py:_atomic_write` and `mcp_tgit_review.py:_atomic_write` implement the same temp-file / fsync / replace discipline, but differ on directory fsync. A carefully parameterized internal primitive can reduce drift.
2. **Local/remote lifecycle facade and catalogs (high value, medium effort):** `mcp_agent.py` repeats the remote-vs-local selection for each lifecycle API, while `remote_agent_adapter.py` separately wraps operations and `remote_agent_service.py` maps handlers. A declarative operation map/facade could reduce omissions as APIs grow.
3. **Git command helpers (medium value, low-to-medium effort):** Git invocation is repeated in MCP Git servers, snapshot/project modules and review handling, but with meaningful differences in bytes/text, cwd, timeout and error policy. Share only a narrow argv/encoding layer if desired.
4. **Integration test fixture setup (medium value, low effort):** Git repository creation and reflink skip logic recur across snapshot and remote integration tests. A small test-only fixture module could reduce setup duplication.
5. **MCP operation catalog/protocol definitions (medium value, medium effort):** operation names and field schemas in `remote_agent_protocol.py` accompany lifecycle maps in `remote_agent_daemon.py`; maintainable from one catalog, but protocol evolution and independent validation require care.
6. **Subprocess execution policy (lower value, medium effort):** `test_subprocess.py` is a specialized async runner, unlike production synchronous subprocesses. Generalizing it risks over-abstraction; share only where there is exact common policy.

## Intentional duplication to retain

- **Trust-boundary validation layers:** `remote_agent_protocol.py:validate_request`, `remote_agent_service.py:_dispatch`, `agent_controller.py:_validate_start_request`, `agent_store.py:validate_agent_id`, and `agent_ipc.py:_validate_request` validate different envelopes at different ingress points. Their overlap is defense in depth and enforces different schemas; do not replace with one caller-trusting validator. Protocol ID rules and filesystem agent-ID rules are not identical.
- **Local and remote adapter separation:** local controller calls in `mcp_agent.py` and remote SSH/protocol calls in `remote_agent_adapter.py` intentionally isolate transport, upload, network failure and serialization concerns. Share only dispatch shape, not transport implementation or trust decisions.
- **Text versus binary Git calls:** `mcp_tgit_review.py:_git` and `_git_bytes` are separate for a reason; binary patch payloads must not be decoded as text.
- **Project versus controller validation:** project config requests in `agent_project.py` are explicitly not authorization; controller sandbox authorization belongs to trusted code. Keep the independent check.
- **Different atomic-write guarantees:** `agent_store.py` fsyncs the containing directory, while review persistence currently does not; unify only with explicit policy and tests, never by silently downgrading durability/security.
- **Standalone MCP servers and response contracts:** separate `FastMCP` instances and tool-local result shapes preserve independently deployable APIs. Similar endpoint declarations are not useful duplication by themselves.
- **Test setup differences:** dirty upload state, linked-worktree coverage, and reflink skip conditions should remain visible even if common mechanics are factored.

## Suggested sequence

1. Resolve configuration ownership/document the `.ini` versus `.toml` mismatch after inspecting deployment consumers; it is a user-facing correctness issue but not safe for blind consolidation.
2. Establish tests around atomic persistence invariants, then extract a narrow helper with options that preserve the observed differences.
3. Add lifecycle backend contract tests and centralize only local/remote dispatch that has identical signatures and result semantics.
4. Consolidate the remote operation catalog only after protocol parity tests; keep every ingress validation boundary.
5. Extract small test fixtures and, if still useful, a narrow Git invocation layer. Avoid a universal subprocess abstraction.
